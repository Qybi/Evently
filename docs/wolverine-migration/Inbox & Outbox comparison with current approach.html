Inbox & outbox: your version and Wolverine's

Ticketing, in Evently.Ticketing.Api, receives the same event the same way with its own schema.

Now

Custom outbox and inbox, polled by Quartz

Each module owns four tables and two jobs. Wolverine only carries the message between the jobs.

  1. 1

    The command handler changes the Event and calls SaveChangesAsync.

  2. 2

    In the same SaveChanges, InsertOutboxMessagesInterceptor turns the entity's domain events into outbox_messages rows. Steps 1 and 2 commit together.

  3. Nothing moves until the next outbox poll.

  4. 3

    ProcessOutboxJob opens a transaction and locks up to 50 unprocessed rows.

  5. 4

    IdempotentDomainEventHandler looks for (event id, handler name) in outbox_message_consumers.

  6. 5

    EventPublishedDomainEventHandler publishes the integration event through Wolverine. The RabbitMQ endpoint is not durable, so this send is outside any database transaction.

  7. 6

    The decorator saves the consumer row with its own SaveChanges, in a separate scope from the job.

  8. 7

    The job sets processed_on_utc and commits. If a handler threw, the error is stored and the row still counts as processed, so it is not retried.

  9. 8

    RabbitMQ delivers to the queue of EventPublishedIntegrationEventConsumer.

  10. 9

    The consumer only copies the event into attendance.inbox_messages.

  11. 10

    Wolverine acks the broker.

  12. Nothing moves until the next inbox poll.

  13. 11

    ProcessInboxJob opens a transaction and locks up to 50 unprocessed rows.

  14. 12

    IdempotentIntegrationEventHandler looks in inbox_message_consumers.

  15. 13

    The real handler runs CreateEventCommand, which commits attendance.events.

  16. 14

    The decorator commits the consumer row separately. A crash between 13 and 14 makes the handler run again on the next poll.

  17. 15

    The job sets processed_on_utc on the inbox row and commits.

With WolverineFx.EntityFrameworkCore

Wolverine's durable inbox and outbox

Envelopes live in Wolverine's tables and are written by your DbContext's transaction. Messages move as soon as a commit lands.

  1. 1

    The command handler changes the Event and saves through IDbContextOutbox<EventsDbContext>, calling SaveChangesAndFlushMessagesAsync.

  2. 2

    In the same transaction, Wolverine collects the domain events from the ChangeTracker (PublishDomainEventsFromEntityFrameworkCore) and stores each one as an incoming envelope for a durable local queue.

  3. 3

    After the commit, the envelope goes straight to the local queue in memory.

  4. 4

    EventPublishedDomainEventHandler, now a Wolverine handler, publishes the integration event. Wolverine stores it as an outgoing envelope.

  5. 5

    In the same transaction, the domain event's envelope is marked Handled.

  6. 6

    After the commit, Wolverine sends to RabbitMQ through a durable outbox endpoint.

  7. 7

    Once RabbitMQ accepts the message, the outgoing envelope row is deleted.

  8. 8

    RabbitMQ delivers to the handler's own queue (MultipleHandlerBehavior.Separated).

  9. 9

    The durable inbox stores the envelope first. An id already seen on that queue is rejected as a duplicate (MessageIdentity.IdAndDestination).

  10. 10

    Wolverine acks the broker.

  11. 11

    EventPublishedIntegrationEventHandler runs right away; CreateEventCommand writes attendance.events.

  12. 12

    In the same transaction, the incoming envelope is marked Handled. The business change and the "done" marker commit together.

  13. ↻

    After a crash or restart, the DurabilityAgent resends outgoing envelopes still in the table and replays incoming ones not marked Handled.

Where the rows live

All schemas sit in one Postgres database. That is what lets Wolverine write its envelope rows in the same transaction as a module's tables, even though they are in different schemas.

To keep envelopes per module, Wolverine 6 has ancillary stores: one store per DbContext, registered with role: MessageStoreRole.Ancillary and .Enroll<EventsDbContext>(). The docs show only the SQL Server form, so check the Postgres overload first.

What the right-hand diagram assumes

// WolverineFx.EntityFrameworkCore, inside AddWolverineInternal
options.PersistMessagesWithPostgresql(databaseConnectionString, schemaName); // already there
options.UseEntityFrameworkCoreTransactions();
options.Policies.AutoApplyTransactions();
options.Policies.UseDurableOutboxOnAllSendingEndpoints();
options.Policies.UseDurableInboxOnAllListeners();
options.Policies.UseDurableLocalQueues();
options.PublishDomainEventsFromEntityFrameworkCore<Entity>(x => x.DomainEvents);
// plus explicit routing of domain event types to local queues:
// DisableConventionalLocalRouting() is on, so they would otherwise go to RabbitMQ
  • Your endpoints call ICommandHandler directly, so Wolverine's middleware does not wrap them. Step 1 needs IDbContextOutbox<TDbContext>, or the command has to go through bus.InvokeAsync.
  • A shorter variant skips the domain-event hop (steps 2 to 5): the command handler publishes the integration event through the same outbox.
  • Delivery stays at-least-once in both designs. What changes is that Wolverine's "done" marker commits with the work, so a replay is caught by the inbox.
